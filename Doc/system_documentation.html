System Documentation

1. System Overview

System Name: Duty Check-in System

Description: A production-ready duty check-in management system for shift-based operations.

2. Architecture

Backend

  • Framework: FastAPI
  • Database: SQLite
  • ORM: SQLAlchemy
  • Authentication: JWT (using jose library)

Frontend

  • Framework: React
  • Build Tool: Vite
  • State Management: Context API
  • Routing: React Router

4. Metadata

Modules

  • Auth: Authentication & Authorization
  • Duties: Duty management (check-in, check-out, attachments)
  • Incidents: Incident reporting and workflow management
  • Users: User management and role assignment

5. Data Flow

Login

UI: LoginPage.jsx → API: POST /auth/login → Backend: auth.py → Database: users

Check-in

UI: CheckinPage.jsx → API: POST /duties/checkin → Backend: duties.py → Database: duties

Incident Creation

UI: IncidentDetailPage.jsx → API: POST /duties/{duty_id}/incidents → Backend: incidents.py → Database: incidents

6. API Structure

Auth Module

  • POST /auth/login - User login
  • GET /users/me - Get current user info

Duties Module

  • POST /duties/checkin - Check-in for duty
  • GET /duties/today - List today's duties
  • POST /duties/{duty_id}/checkout - Check-out from duty
  • GET /duties/{duty_id}/attachments - List duty attachments
  • POST /duties/{duty_id}/upload - Upload file for duty

Incidents Module

  • POST /duties/{duty_id}/incidents - Create incident
  • GET /incidents/{incident_id} - Get incident details
  • PATCH /incidents/{incident_id}/workflow - Update incident workflow
  • POST /incidents/{incident_id}/upload - Upload file for incident

Users Module

  • GET /users/ - List all users
  • GET /users/assignable - List assignable users
  • GET /users/me/roles - Get current user's roles

7. Business Rules

Validation Rules

  • email must be a valid email format
  • role_id and shift_id must exist in the database

Required Fields

  • User: employee_code, full_name, email, password
  • Duty: role_id, shift_id
  • Incident: None (all fields are optional)

Constraints

  • All tables have a primary key (id)
  • users.email and users.employee_code must be unique
  • roles.name must be unique
  • user_roles uses a composite primary key (user_id, role_id)

Logic Before Commit

  • Incident: Created with default status "OPEN"
  • Role: Checks for duplicate role names before creation
  • Duty: Validates role_id and shift_id before creation
